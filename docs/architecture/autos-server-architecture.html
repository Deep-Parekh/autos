Autos Server Architecture

How Autos turns Jira bugs into reviewed feature branches on one Ubuntu host: two long-running trusted processes, and short-lived agent containers that exist only while a ticket is being worked.

Trusted Autos code Untrusted coding agents (sandboxed) External services Persistent storage
One ticket, start to finish

What happens to a bug

  1. The controller reads the saved Jira filter and queues each new eligible bug. Ineligible tickets are blocked with a reason, and the queue keeps going.
  2. It looks up the project in the Confluence branch map, fetches the development branch, pins its exact commit, and creates an isolated workspace on deep/<KEY>.
  3. It reads AGENTS.md and other instruction files from that commit. Every agent, whichever provider it uses, gets them as binding project rules.
  4. The supervisor starts an SWE container. If a provider hits a limit, the next provider in the chain continues from a progress handoff.
  5. Build and test checks run in a network-less container on a copy of the source.
  6. Independent QA and reviewer agents, each in a fresh read-only session, judge the exact candidate. Findings go back to SWE for up to two repair rounds.
  7. Trusted Git commits only the reviewed content, optionally pushes the feature branch, and writes the evidence. The job ends READY_FOR_HUMAN or BLOCKED.
  8. You review the branch and evidence, then merge it yourself or run autos revise with notes.

Every agent container runs non-root, with a read-only root filesystem, all capabilities dropped, memory, CPU and process limits, and a timeout.

Always on vs. on demand
Always running: the controller (Compose) and the supervisor (systemd). Both restart on failure.
Only while a ticket is worked: the agent and check containers, which are removed after each step.
Idle host: no agent containers, only a poll every few minutes.
Built-in guarantees
Read-only Atlassian: no Jira or Confluence writes, PRs, merges, rebases or deploys.
No stale approvals: READY_FOR_HUMAN needs passing checks, QA and review of the same final candidate.
Scales by config: one ticket at a time by default. On a larger host, jobs.max_parallel allows up to 8.
Watching it
autos status shows slots, the active tickets, stage, agent and elapsed time.
autos watch streams every step live, including provider fallbacks.
Per-job evidence: summary.md, rounds.json, checks, QA and review.
